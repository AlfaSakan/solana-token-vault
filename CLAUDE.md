## Lessons Learned

Bug/gotcha nyata yang ditemukan saat implementasi — jangan ulangi:

### `declare_id!()` placeholder yang "kelihatan" seperti pubkey belum tentu valid base58 32-byte
Skeleton awal pakai `declare_id!("TokenVau1t11111111111111111111111111111111")` (dan `Anchor.toml` `token_vault = "..."` sama) — 42 karakter, terlihat plausible tapi bukan hasil decode base58 valid 32 byte. `anchor build` gagal dengan pesan generik `Error: String is the wrong size`, tidak menyebut field/file mana. Selalu generate program id dari `solana-keygen new -o target/deploy/<program>-keypair.json` lalu `solana-keygen pubkey` itu, jangan tulis placeholder string manual — walau sekadar untuk skeleton/scaffold sebelum instruksi diisi.

### Toolchain Anchor/Solana CLI tidak auto-terinstall — `anchor build`/test butuh setup manual sekali di awal
Mesin dev baru tidak punya `solana`/`anchor`/`avm` sama sekali. Urutan install yang terbukti jalan: (1) Solana CLI via installer resmi Anza (`sh -c "$(curl -sSfL https://release.anza.xyz/stable/install)"`), (2) `cargo install --git https://github.com/coral-xyz/anchor avm --locked --force`, (3) `avm install <versi pinned di Cargo.toml>` (mis. `0.30.1`), (4) `avm use <versi>` — langkah ini otomatis switch `solana-install` ke versi Solana CLI yang cocok dengan Anchor version tsb (mis. Anchor 0.30.1 → Solana 1.18.17), jangan asumsikan versi Solana CLI stable terbaru otomatis kompatibel. Build `anchor-cli` dari source lewat cargo makan waktu lama (10-20 menit tergantung network) — jalankan di background, jangan diasumsikan gagal kalau belum ada output beberapa menit.

### `anchor build` di toolchain 2026 vs Anchor 0.30.1 (rilis 2024): cargo-build-sbf's bundled rustc terlalu tua untuk crates.io "hari ini" — harus pin banyak dependency manual, dan pin di direktori repo, bukan cuma di Cargo.lock
`cargo-build-sbf` (dibawa oleh Solana CLI 1.18.17, dipilih otomatis oleh `avm use 0.30.1`) membawa rustc custom fork versi `1.75.0-dev` yang jauh lebih tua dari tanggal sistem saat ini. `cargo generate-lockfile` dari cargo modern (default rustup toolchain, jauh lebih baru) meresolve ke versi-versi TERBARU dependency yang ternyata butuh Rust edition2024 (distabilkan ~1.85) — build gagal beruntun dengan pesan `feature edition2024 is required` untuk satu crate demi satu crate (`crypto-common`→`block-buffer`→`zeroize_derive`→`toml_edit`→`indexmap`/`hashbrown`→dst, rantainya dalam sampai belasan crate). Fix: (1) `rustup override set solana` di root repo supaya SEMUA invocation `cargo` polos (bukan cuma `cargo-build-sbf`) dalam direktori itu otomatis pakai toolchain tua yang sama — tanpa ini, `anchor build` yang secara internal mencampur dua compiler (satu untuk `.so` lewat `cargo-build-sbf`, satu untuk IDL-gen lewat `cargo` polos) bikin `Cargo.lock` bolak-balik ke-upgrade ke format v4 lalu gagal dibaca compiler yang lebih tua (`lock file version 4 requires -Znext-lockfile-bump`). (2) Untuk tiap crate yang gagal karena edition2024/MSRV, jalankan `cargo tree -i <crate>` (pakai cargo SISTEM yang modern, bukan `rustup run solana cargo tree` — yang terakhir ini gagal duluan karena tidak bisa parse manifest crate yang mau diperiksa) untuk cari siapa consumer teratas yang menariknya, lalu `rustup run solana cargo update -p <crate>@<versi-baru> --precise <versi-lama>` untuk turunkan versi itu. Ulangi sampai `anchor build` lolos resolusi dependency. Set pin final yang terbukti jalan untuk kombinasi anchor-lang 0.30.1 + solana-program 1.18.26 + rustc 1.75.0-dev: `blake3@1.5.5`, `zeroize_derive@1.4.2`, `borsh@1.5.1` (+`borsh-derive@1.5.1`), `proc-macro-crate@3.1.0`, `indexmap@2.7.1`, `unicode-segmentation@1.10.1`, `jobserver@0.1.32`, `thiserror@1.0.56`, `syn@2.0.60`, `bitflags@2.4.2`, `serde@1.0.197`+`serde_derive@1.0.197`, `serde_json@1.0.111`, `serde_bytes@0.11.14`, `bytemuck@1.16.3`+`bytemuck_derive@1.7.0`, `web-sys@0.3.69`+`js-sys@0.3.69`, `wasm-bindgen@0.2.92`, `proc-macro2@1.0.86`.

### `anchor build`'s IDL-generation step (bukan `.so` build) benar-benar rusak di kombinasi Anchor 0.30.1 + rustc fork 1.75.0-dev Solana — pakai `--no-idl` dan IDL hand-maintained
Bahkan setelah semua pin edition2024/MSRV di atas beres dan `.so` sukses ter-compile (`anchor build --no-idl` jalan mulus), langkah generate IDL (`cargo build --features idl-build` internal) tetap gagal: `anchor-syn`'s kode `idl/defined.rs` memanggil `proc_macro2::Span::call_site().source_file()` di balik cfg `procmacro2_semver_exempt` (fitur untuk introspeksi source path type alias) — method ini butuh compiler nightly asli yang expose `proc_macro::SourceFile`, dan fork rustc 1.75.0-dev milik Solana platform-tools TIDAK punya symbol itu sama sekali (beda dari rustc mainline 1.75 nightly resmi), walau proc-macro2 versi lama (1.0.86, sebelum method itu dihapus total di versi lebih baru) sudah dipin. Ini dead-end tanpa fork rustc yang berbeda atau anchor-cli yang lebih baru. Solusi: `anchor build --no-idl` (skip IDL codegen, `.so` tetap ter-build normal), lalu tulis `idl/token_vault.json` + `idl/token_vault.ts` manual di root repo (BUKAN di `target/idl`/`target/types` — itu di-gitignore dan hilang tiap `anchor build`). Field/account name di IDL pakai **camelCase** (`adminAuthority`, bukan `admin_authority`) — itu konvensi asli Anchor buat IDL JS-facing, borsh decode tetap urut posisi field jadi rename aman. Discriminator dihitung manual: instruksi = 8 byte pertama `sha256("global:<nama_instruksi_snake_case>")`, account = 8 byte pertama `sha256("account:<NamaStructPascalCase>")`. Update `idl/*.json`+`.ts` manual tiap kali instruksi/account/error baru ditambah di `lib.rs` — lihat `idl/README.md`.

### `anchor-litesvm`'s error-detection (`sendWithErr`) diam-diam gagal kalau ada DUA copy package `litesvm` ter-install — `instanceof` check-nya silent-false, transaksi gagal dianggap sukses
`anchor-litesvm` (versi 0.2.1, terakhir update setahun lalu) pin dependency `litesvm: "^0.3.3"` di package.json-nya sendiri. Kalau top-level `package.json` proyek pin versi `litesvm` yang beda (mis. `^0.4.0`, yang TIDAK match range `^0.3.3` karena aturan semver untuk versi `0.x` — bump minor dianggap breaking), package manager (yarn/npm) install DUA copy `litesvm` terpisah: satu di `node_modules/litesvm`, satu lagi di `node_modules/anchor-litesvm/node_modules/litesvm`. `sendWithErr` (internal `anchor-litesvm`, dipanggil dari `sendAndConfirm`, yang dipanggil dari `.rpc()`) mengecek `res instanceof litesvm_1.FailedTransactionMetadata` — tapi `litesvm_1` di sini adalah class dari copy `anchor-litesvm`'s SENDIRI, sedangkan `res` yang dikembalikan berasal dari `LiteSVM` instance yang dibuat test kita pakai TOP-LEVEL `litesvm`. Dua class `FailedTransactionMetadata` yang berbeda identity → `instanceof` selalu `false` → error transaksi diam-diam DIBUANG, `.rpc()` resolve sukses padahal transaksi sebenarnya gagal on-chain (compute log-nya kelihatan errornya kalau di-dump manual, tapi test yang cuma cek "does it throw" akan false-negative: assert "should fail" gagal walau program-nya sudah benar). Gejalanya persis seperti bug program (test "calling initialize twice should fail" gagal), padahal root cause-nya di layer test tooling. Fix: pin `litesvm` di top-level `package.json` PERSIS sama range yang dipakai `anchor-litesvm` (cek `node_modules/anchor-litesvm/package.json`), lalu `rm -rf node_modules yarn.lock && yarn install` supaya package manager dedupe jadi satu copy — verifikasi dengan `find node_modules -maxdepth 3 -type d -name litesvm` (harus cuma satu hasil).

### LiteSVM: transaksi kedua dengan blockhash+instruksi+signer identik dianggap "sudah pernah diproses" — bukan re-execute — kalau mau test "call X twice harus gagal karena alasan LOGIKA (bukan duplicate tx)", expire blockhash-nya dulu
Manggil instruksi yang sama dua kali berturut-turut dalam satu test synchronous (tanpa slot/blockhash berubah) menghasilkan signature identik; LiteSVM/anchor-litesvm nge-treat itu sebagai "transaction already processed" dan resolve sukses TANPA benar-benar re-execute instruksinya — jadi assertion "should throw" bisa false-negative walau program-nya benar (dan false-positive kalau programnya salah, karena dua-duanya sama-sama tidak error). Sebelum transaksi kedua yang sengaja mau di-test gagal karena constraint (mis. `init` pada account yang sudah ada), panggil `svm.expireBlockhash()` supaya blockhash-nya beda, baru transaksi kedua itu benar-benar distinct dan benar-benar di-eksekusi ulang oleh VM.

### `ts-mocha`/`mocha` dengan glob unquoted di `package.json`/`Anchor.toml` scripts (`tests/**/*.ts`) diam-diam jadi 0 test kalau dijalankan via `yarn run`/`npm run`
Shell yang menjalankan npm/yarn script meng-expand glob SEBELUM sampai ke mocha (globstar `**` seringkali tidak ke-enable di shell non-interaktif), jadi mocha menerima daftar file yang salah/kosong dan silently melaporkan "0 passing" — bukan error, gampang kelewat kalau cuma lihat "no failures". Selalu quote pattern glob test di package.json scripts (`"tests/**/*.ts"`), supaya mocha's sendiri (bukan shell) yang expand — lolos test manual langsung (`npx ts-mocha ... "tests/**/*.ts"`) tapi gagal lewat `yarn test` adalah sinyal persis masalah ini.

### Test harness LiteSVM + Anchor client: pakai `anchor-litesvm` (`LiteSVMProvider`), bukan `AnchorProvider` biasa
`AnchorProvider` bawaan `@coral-xyz/anchor` butuh `Connection` RPC asli, tidak bisa langsung dipasang di atas `litesvm` (LiteSVM jalan in-process, tanpa RPC endpoint). Package `anchor-litesvm` expose `LiteSVMProvider` yang implement interface `Provider` dari Anchor (proxy `getAccountInfo`/`sendTransaction`/dst ke method `litesvm`-nya langsung) — pasang itu sebagai provider ke `new Program(idl, provider)`, dapat full `program.methods.xxx().accounts({...}).rpc()` API seperti biasa tanpa perlu encode instruksi manual pakai `BorshCoder`.

### Test harness "reusable across tickets" = factory function, bukan satu instance LiteSVM yang di-share lintas file test
Acceptance criteria issue #2 minta harness "reusable... without duplication". Desain yang benar: `createTestContext()` di `tests/helpers/context.ts` yang di-panggil ulang (fresh LiteSVM + program load) tiap `beforeEach`/test case — bukan satu `LiteSVM` instance module-level yang di-share semua file test. Sharing satu instance akan bikin urutan test antar file/ticket saling bergantung (state `initialize` dari test lain bocor ke test yang harusnya mulai dari nol), sementara yang dimaksud "no duplication" cuma soal boilerplate loading `.so`/IDL-nya yang ditulis sekali, dipakai berkali-kali.

### Parameter numerik admin-supplied di instruksi `create_pool` (bps, durasi) butuh `require!` bounds check di situ juga — bukan cuma di instruksi consumer-nya belakangan
Sebelum fix di issue #7, `create_pool` menerima `early_withdrawal_penalty_bps: u16` dan `lock_duration_seconds: i64` tanpa validasi apa pun. Root `Cargo.toml` set `overflow-checks = true`, jadi Pool yang dibuat dengan `early_withdrawal_penalty_bps > 10_000` bikin `amount - penalty` underflow di `withdraw_early`, dan `lock_duration_seconds <= 0` bikin cast `as u128` di formula reward `withdraw` overflow — dua-duanya panic saat instruksi WITHDRAW dipanggil, bukan saat `create_pool` dipanggil, sehingga gampang lolos test kalau cuma nge-test happy-path `create_pool`. Karena Pool immutable sekali dibuat (CONTEXT.md), Pool yang sudah kadung dibuat dengan parameter invalid itu PERMANEN rusak — tidak ada instruksi "update pool" untuk memperbaikinya. Selalu taruh `require!` bounds check di instruksi `init`/pembuat account yang immutable, tepat di titik parameter itu pertama masuk, jangan andalkan defensive check di instruksi consumer yang baru jalan belakangan.

### Repo ini pakai stacked branches/PR per issue — branch baru dibuat dari branch issue SEBELUMNYA, bukan dari `main`
`main` cuma berisi scaffold awal (2 commit, sebelum issue #2). Semua kerjaan issue #2–#6 numpuk berurutan sebagai PR yang saling base ke branch issue sebelumnya (mis. PR untuk `issue-3-create-pool` nge-base ke `issue-2-initialize-and-test-harness`, dst — dicek via `gh pr list --state all --json number,baseRefName,headRefName`), bukan tiap issue independent dari `main`. Sebelum `git checkout -b issue-N-xxx` untuk issue baru, cek dulu PR/branch issue terakhir yang belum di-merge, branch dari situ, dan set base PR baru ke branch itu — branch dari `main` malah kehilangan semua kode issue sebelumnya yang belum merge.
